# 2026-09-12 — Upload pipeline trace harness, and what it found

The user asked to see what actually happens when a batch of files goes through the uploader:
a random batch of ~15 files in differently-named subfolders, then the same thing at 150 files, with
mock data, step by step, including where the Search Object is created and how it gets filled — and
an explicit statement of what is mock and what is real.

## What shipped

A headless trace harness under `apps/web/src/app/core/upload/trace/`, driven by
`scripts/trace-upload-pipeline.mjs` (`npm run trace:upload`). It is a Vitest spec, so it runs the
**real** Angular services — `UploadManagerService`, `classifyBatch`, the token classifier and layer
map, the shipped AT geo assets, the branch gates, content hashing, the queue and phase FSM, all
three pipelines, `persistUploadFile` — against an in-memory Supabase, a 12-row stub gazetteer in
place of Photon, injected EXIF, and synthetic single-byte files. 150 files trace in ~8 s.

Three runs, because the pipeline has three shapes: folder + `required` (address pipeline), flat
multi-file + `optional` (persistence path, which is where the storage key and the `media_items`
insert payload become visible), and folder + `optional`.

Walkthrough and the real-vs-mock table: [`docs/playbooks/upload-pipeline-trace.md`](../playbooks/upload-pipeline-trace.md).
The harness prints the same table itself, because a trace that needs an external legend misleads.

## What it found (no fixes in this change — the pipeline is Sensitive class)

Four of these were not visible by reading the code; they came out of running it.

1. **A camera file name injects a postcode.** `IMG_1274.jpg` under `AT/Wien/1090/Währinger Straße 12/`
   resolves as postcode **1274**. Pass 2 classifies a 4-digit token as a postcode once the country
   is known, and `adminLevelMap` collapse keeps the **lowest** level index — level 0 is the file
   name — so the file name beats the folder. Both rules are as specified;
   `isWeakFilenameStreetLevel` guards the street case and has no numeric counterpart. Consequence:
   `IMG_1274` and `IMG_1275` in one folder get different `groupingKey`s, so two photos of one
   building geocode twice and open two trays.
2. **`Wien` resolves to `Schottwien`.** `at-gemeinden-bev.json` carries `Wien-Alsergrund` … and
   `Schottwien`, but no plain `Wien`. The Fuse match scores `Schottwien` at 0.992, over the 0.98
   write threshold. Every Vienna folder gets `city = Schottwien`, which then disagrees with
   `state = Wien` and opens an `admin_level_conflict` tray for an unambiguous path.
3. **City classification needs an explicit country segment.** The gazetteer is only consulted when
   `country === 'AT'`, so `Graz/Annenstraße 10/DSC_0001.jpg` produces an **empty** Search Object —
   `Graz` becomes a street fragment and `groupingKey` is `|||||`.
4. **Ordinary file names form competing street packages.** `foto.jpg`, `Abnahmeprotokoll.pdf`,
   `Kopie von IMG_1274.jpg` each build a filename layer package that conflicts with the folder
   package and opens a `layer_package` tray.
5. **Volume.** 150 files with plain camera names: **131 tray questions**, 9 automatic placements.
   The same 150 through the persistence path: 144 rows written, 6 duplicates skipped.
6. **`locationRequirementMode: 'optional'` does not skip the address pipeline** on a folder submit.
   The trigger matrix in `upload-address-resolution.phases.md` says it does; in fact `classifyBatch`
   runs regardless and its trays still gate — 13 of 15 files parked in `awaiting_disambiguation`
   before hashing. Only the per-job geocode step reads the mode.

(1), (2) and (6) are spec-level, not implementation slips, so they need a spec decision before a fix.

## Then: database scale

The user's follow-up was the important one — "folders with thousands of files, or tens or hundreds
of thousands, if a company uploads their whole database". That is not the same test, and the
end-to-end harness cannot answer it: measured wall time is 8 s at 150 files, 35 s at 1 000, 72 s at
2 000, ~3.5 min at 5 000.

So `--scale=N` measures the two costs that dominate instead, both against real production code,
streaming paths by index so nothing is materialised:

- **Classification is ~9 ms per file** and it is the fuzzy gazetteer.
  `path-token-classifier.ts:86` builds `new Fuse(items, …)` **per candidate token** and then
  searches 2 114 municipalities with `threshold: 0.4` across two keys. Measured apart: index build
  1.06 ms, search 2.75 ms — so caching the index buys ~30 % and the fuzzy search is the rest. A
  normalized exact-match map consulted before Fuse would remove it for nearly every token.
  This work happens **synchronously inside `classifyBatch`, before the queue drains**, so it is
  time-to-first-byte: ~15 min for 100 000 files, ~2.5 h for a million.
- **The job store is `O(n)` per write, so `O(n²)` per batch.**
  `upload-job-state.service.ts:126` — `_jobs.update((prev) => prev.map(...))` — reallocates the
  whole job array on every field write, and `findJob` at :122 is a linear scan. Measured
  `updateJob`: 0.002 ms at 100 jobs, 0.016 at 1 000, 0.080 at 5 000, **0.573 at 20 000**. At ~15
  writes per job that is 2.9 min for a 20 000-file batch and ~72 min for 100 000. An id-keyed Map
  makes both O(1) and is the highest-leverage change for large batches.
- **Trays do not scale either.** ~45 000 tray questions for 100 000 files. The scale tier runs the
  corpus twice — `camera` naming (`IMG_2001.jpg`) and `neutral` naming (a 6-digit leaf that cannot
  parse as an AT postcode) — and the difference is stark: with camera names **100 %** of groups need
  a question and `branch_a` is **zero**; with neutral names 27 % of the corpus goes straight to
  `branch_a` and the tray share drops to 66 %. Finding (1) above is therefore also the cheapest
  available scale win.

Verdict: a 100 000-file folder is not viable today — roughly 1.5 h of synchronous main-thread work
before uploading is properly under way, plus 45 000 questions. Neither is a network limit.

Two artifacts of my own generator were found and fixed while measuring, and both had distorted a
run: content bodies were a single fill byte cycling every 200 files, so at 5 000 files the corpus
was 82 % accidental duplicates (bodies now carry a per-index seed in their first four bytes); and
the settle budget was a poll count worth 10 s, so a 5 000-file batch reported jobs still mid-flight
(now a 180 s wall-clock deadline, and the count is printed rather than swallowed).

## Owner review of the decisions, same day

The owner answered four of the six decisions, and two of the answers changed the work rather than
just approving it.

**D-01 was a wording failure on my side, not a disagreement.** I wrote "file names must not write
admin fields" and the owner read "admin fields" as possibly covering the street fields — reasonably,
because the sentence never said which four fields it meant. Street names *do* appear in file names
(`Mühlenstraße`) and must reach the Search Object. `AdminFieldKey` is
`country | state | city | postcode` and nothing else (`upload-address-level-map.types.ts:6`), so the
requirement was never in scope. Two lessons, both cheap to apply: name the enum when you write a rule
about "fields", and pin a stated requirement with a scenario before proposing a change near it. S16
(`Baustelle Nord/Mühlenstraße 12.jpg`) and S17 (`… /1090 Mühlenstraße 12.jpg`) now do that.

Pinning it immediately paid for itself twice:

- S17 shows the case my own trade-off warned about **already does not work**: a file-name postcode
  with no country anywhere in the path is dropped entirely (pass 2 needs a country; the house-number
  fallback caps at three digits). So the proposal gives up less than I claimed, and F-01 carries a
  correction saying so.
- S16 turned up a new finding, **F-11**, which is the actual obstacle to the owner's requirement: a
  folder segment with no address (`Baustelle Nord`) becomes a street-level layer package at
  confidence 0.5, competes with the file name's package, and the flat Search Object then keeps
  **neither** street — `groupingKey` `|||||12`. The same file through the flat multi-file path
  resolves to `||||muhlenstraße|12` and uploads. The parse is right; the folder destroys it.

**D-03 was rejected, and the rejection produced a better answer than mine.** I proposed deriving the
country from an org-level home country. The owner's objection — an organisation may work in Germany
*and* Austria — kills the primitive, and looking for a replacement found that the mechanism already
exists in the tree and the Search Object path stopped using it: `CITY_REGISTRY` records carry their
own `country`, and `findCityBySegment` returns `{ city, country }` on an exact match. Its only callers
sit in `location-path-parser.service.ts`, which the SO spec marks non-normative. The normative path
instead gates an AT-only fuzzy gazetteer behind `useAtGeo = countryCode === 'AT'` — so `Graz/…` fails
because the new code asks a country-scoped dataset for the country. The re-derived recommendation is
exact-country-carrying-lookup-first with the country *derived* from the match, cross-country
ambiguity left unresolved rather than guessed, and the org country list demoted to an optional
narrowing filter. It also makes `Wien` → `Schottwien` unreachable, so it partly absorbs F-02.

The general lesson, and the one most likely to recur: **before inventing a primitive (an org setting,
a new field, a new default), grep for the one that already exists.** The legacy parser had it, and the
rewrite dropped it silently — the same shape TRAP-010 describes for dead code, running in the other
direction.

D-02 and D-05 were accepted as recommended; D-05 restated as a standing rule — spec first, then code.
D-04 (archive-import mode) and D-06 (the `test` gate) are still open.

## Phase 0 — unblocking the gate, and what that uncovered

Owner picked D-01 = A′, D-04 = a dedicated archive-import mode, and Phase 0 to start.

**0.1 — the seven type errors.** Fixed with **no** `as unknown as` cast, which turned out to be
forced rather than virtuous: `UploadService` and `UploadQueueService` are classes with private
injected fields, so a structural full fake cannot satisfy them at all — the only cast-free route is
to narrow the deps bags to the members they actually call. Two files in the same path already did
that (`upload-dedup-skip.util.ts:11`, `upload-heic-prepare.util.ts:22`), so it is local convention,
not an invention. Narrowed: `HeicPrepareDeps.uploadService`, `UploadDedupCheckDeps.queue` and
`.uploadService`, its `ctx` (6 of `PipelineContext`'s 14 members), `PreResolveDeps`,
`routeJobToMissingData`, and the replace-finish deps. Three test fakes corrected. All type-level —
no runtime code changed, and `ng build` plus the full suite prove the real callers still satisfy them.

Two traps in the doing:

- **`npx tsc -p tsconfig.spec.json --noEmit` is not the gate.** It went clean while the `ng test`
  bundle still failed, because the two resolve *different* `environments/environment.ts` (file
  replacements), and `environment.supabase` has a different shape per configuration. The fix was to
  export the production module's own `DevSupabaseEnv` — all members optional, exactly because of
  that — and have the spec cast to it instead of re-declaring a shape that only fits one build.
- The 2026-09-08 audit had already recorded this error class as **T3/T4** and warned "no conclusion
  in any later phase may be supported by 'the tests pass'". Eleven errors then, seven left today.
  Nobody was wrong about it; it just sat there, because a soft gate reported it as known debt.

**0.2 — the gate can now tell "did not run" from "ran and N failed."** `verify.mjs` checks may
declare `resultFile` + `evidence()`; the runner deletes the file, runs the check, and a missing or
empty report is a **hard** failure regardless of `soft`. Verified red-first by appending a type error
to a trace file: the gate went from `✓ verify passed, with known debt` to
`✗ test produced no result: no test report was written — the suite did not run`. The measured counts
now print on every run, so the summary states an observation rather than a memory.

**What running the suite immediately revealed — F-12.** Two identical runs on an unchanged tree:
**34 failures across 13 files, then 39 across 14.** The swing file is
`core/upload/upload.service.spec.ts` (5 EXIF assertions); it passes in isolation, as does
`core/supabase/supabase-runtime-config.spec.ts`, which fails in every full run. Reproduced with the
new harness excluded, so it is not the harness. The old debt note's *number* was right — the first
run reported exactly 34 — which is precisely why the false half of the sentence survived: the number
matched, so nobody read on. A ratchet on a count that moves by 5 is not a ratchet, so Phase 0 gained
step **0.4** (fix the isolation) and the debt note now says outright that the measured line, not the
note, is the number that counts.

## 0.4 — the "flaky" tests were a build cache

Continued 2026-09-13. Calling F-12 flakiness was the lazy reading, and it was wrong. Deleting
`apps/web/node_modules/.vite` before each run makes the suite **deterministic**: five consecutive
cold runs, 39 failures across 14 files, identical every time. Warm, the same tree alternates
39 / 34 / 39. The cached dependency metadata changes the order Vitest assigns spec files to workers,
and the cross-file pollution only bites in some orders. CI always starts cold, so **39/14 is the real
number** and the 34 that the debt note had carried since 2026-09-10 was a warm-cache local artifact.
Clearing the cache costs nothing measurable (52 s cold, 54 s warm), so `verify.mjs` now does it via a
`clean` field. The measurement is trustworthy; the pollution is untouched, and saying otherwise would
be the same mistake in the other direction.

Four hypotheses died on the way, each by measurement rather than argument: all 53 `core/upload` specs
pass together (331 tests), so the polluter is outside; neither of the two files overlapping the
failure reproduces it pairwise; neither do the six specs that call `vi.restoreAllMocks()`; and
`optimizeDeps.exclude` on the exifr entry point changes nothing, which killed my favourite theory
(that the mock and the production import landed on two module instances). It needs a larger set than
any pair — which is why 0.4b is a real task and not a one-liner.

On the way to that, **F-13**: `ng test` does not load `vitest.config.ts` at all. Proven by appending
`this is not valid typescript at all ((((` to it and watching 46 tests pass. So the repo has a config
with a load-bearing `heic2any` → mock alias that CI never applies, and `npx vitest run <file>` and
`npm run test` are two different configurations for the same spec. Nothing looked broken because the
two settings that would have shown it — jsdom and the setup file — happen to match the builder's own
defaults. Also worth knowing: `--runner-config=true` is read as a *path* named `true` and fails; on
the command line it wants a filename.

The lesson for the diary, since it cost an hour: **"flaky" is a hypothesis, not a diagnosis.** The
cheap test for it is to remove one piece of run-to-run state at a time and see whether the outcome
stops moving. Here the first thing removed — a build cache nobody suspected — made it deterministic.

## Phase 1.1–1.2 — the filename admin gate, narrowed by a test that objected

2026-09-13. Spec first, per D-05: `upload-search-object.md` § Admin level map gained a **filename
gate** row and pass 2's postcode rule now references it. Then five red tests, then the code.

The interesting part is that **an existing test made the rule better.** My A′ wording gated *all*
admin fields from a filename, and `records filename-derived admin tokens at level 0` promptly failed:
`Graz.jpg` under `AT/Wien/` deliberately contributes `city = Graz`. Every measured instance of the
defect is a *number*, and a camera writes `IMG_1274.jpg`, never `Graz.jpg` — so the gate narrowed to
**numeric** admin tokens only. Same fix, no collateral, and the deliberate behaviour someone wrote a
test for survives. Had I updated that test to match my rule instead of listening to it, the loss
would have shipped silently.

Gating on **confidence ≥ 0.9 for a street-level token** rather than on a filename pattern turned out
to matter too: it closes `Kopie von IMG_1274.jpg`, which the pattern-based
`isWeakFilenameStreetLevel` does not, because that name does produce a street fragment — just a
worthless one at 0.5.

Measured: tray questions on the curated corpus **13 → 9**; `SO-FILENAME-OVERRIDES-FOLDER` reports
nothing. At 500 generated paths the `camera` and `neutral` naming runs are now **identical** (391
groups, 269 needing a tray, same histogram) where camera naming previously put 100 % of groups in a
tray with `branch_a` at zero. That equality is the proof: file naming no longer changes what the
pipeline does. The grouping-key assertion I had to drop from the harness on day one is back in, green.

Two process notes worth keeping: my new tests first landed inside `describe('isSearchObjectComplete')`
because I appended before the file's last brace — they test `buildSearchObjectFromRelativePath`, so
they are now their own top-level describes. And the change cost 4 lint warnings (an over-long
function, complexity 16, an over-long arrow); extracting one predicate and splitting the describe put
the count back to the baseline 147/1064 exactly. The ratchet only works if you measure both sides.

## Phase 1.3–1.4 — the gazetteer, and the bug it uncovered

Spec first again: pass 1 step 5 now says exact match first, Fuse only as fallback, and a fuzzy hit
whose length differs from the token by more than `max(2, ⌈len × 0.25⌉)` is rejected. Then four red
tests, then the code: an exact name/alias index memoized per dataset (which also removes one
per-token Fuse rebuild, so it pays part of F-06 forward), plus the length bound.

`Wien` (4) against `Schottwien` (10) blows the bound, so the gazetteer gap now fails visibly and the
Vienna postcodes in `at-plz.json` supply the city through expansion instead. Curated corpus:
`SO-CITY-NOT-IN-PATH` 6 → 0. At 500 generated paths `admin_conflict` 53 → 0, `branch_a` 129 → 166.

One test I wrote had to go: I asserted that a one-character typo still matches, and it does not —
`Klagenfurth` matched nothing *before* the bound either, because the 0.9 confidence floor already
rejects near misses. Asserting it would have been adding capability the decision never asked for. The
test now records the actual behaviour so the bound is not blamed for it later.

**Then the run exited 1 with every test passing**, which is how F-14 surfaced:
`registerSourceConflictGroupAsync` writes `awaiting_disambiguation` while the job is in `hashing`;
the FSM reports the edge as illegal and applies it; hashing's completion then sets `dedup_check` and
**erases the gate**. The tray waits for an answer, the job waits for nothing, and it strands.

I nearly added `hashing → awaiting_disambiguation` to the transition map to quiet the assertion.
That would have removed the only signal that found this while leaving the job stranded — the
assertion was telling the truth. Checking first paid off twice more: the sibling edge
`hashing → conflict_check` already fires on the unmodified tree, and the 5 000-file run from
2026-09-12 — before any fix here — ended with **13 jobs stranded in `dedup_check`**. So F-14 is
pre-existing and my change only made it reachable in a 17-file corpus. It is now Phase 1.7, Sensitive,
with its own red test.

Two smaller things. `GROUP-SPLIT-WITHIN-FOLDER` now reports *more* than before, which is the check
getting sharper: while admin conflicts existed, four files in one folder shared one conflict-signature
group, hiding that their `street` values already differed. And my own findings checker claimed to
exclude postcode-expanded cities from `SO-CITY-NOT-IN-PATH` while never implementing the exclusion —
it reported every PLZ expansion as a finding. Fixed. A checker whose message and code disagree is the
same class of defect as a debt note whose number and sentence disagree.

## The owner's path, and a model they had misread (F-15, TRAP-016)

The owner said they had assumed every address field is a map of level → value with several values
possible, and offered `Mödling/Wilhelminenstraße 141/Wilhelminenstr 141, 1160 Wien` — two
contradictory cities, which is exactly what such a map is for.

Half right, and the half that is wrong is load-bearing: `adminLevelMap` covers **four** fields
(`country`, `state`, `city`, `postcode`). Street-level fields are excluded by one easily-missed spec
row and live as `AddressLayerEntry[]` — one whole package per folder prefix — where fragments are
**concatenated**, not kept as alternatives. `sources[]` lists every write but carries no level. So
competing street readings are per-path-prefix, never per-field-per-level. Filed as TRAP-016, because
the misreading is the natural one and it came from the person who commissioned the spec.

Running their path was worse than I expected. Result: `country=null state=null postcode=null
city=null street=null houseNumber=141`, `groupingKey |||||141`, `adminLevelMap {}`. A file whose name
contains a postal address good enough to geocode verbatim produces an **empty** Search Object. Three
independently-correct rules compose to it: no country token means the gazetteer is never consulted, so
`Mödling` and `Wien` are street fragments rather than cities; `1160` is not a postcode (no country) and
not a house number (four digits), so it is dropped without even reaching `postcodeCandidates`; and the
leftover fragments form three competing layer packages, so the flat `street` stays null. The
`adminLevelMap` machinery built for "two cities at different levels" never engages, because nothing
was ever classified as a city.

Filed as F-15 and pinned as scenario S18. It is the strongest argument yet for D-03: derive the
country from a city match instead of requiring it as input, and this path becomes the tray question it
should always have been.

## Phase 2.1 — the country comes from the place (D-03, F-03, F-15)

The owner rejected the first D-03 recommendation for a good reason: defaulting the country from the
organisation has no answer for an org working in Germany *and* Austria, and a wrong default is worse
than none because it is invisible. Their instruction for the replacement was procedural and I followed
it literally — "die Spec gewinnt. Das muss alles in den Specs geschrieben sein und dann kommt der
Code". So: a new child spec
([`upload-search-object.country-derivation.md`](../specs/service/media-upload-service/upload-search-object.country-derivation.md)),
a `countryProvenance` row in the parent's field table, an amended pass-1 step 5 — and only then the
implementation.

The mechanism was already in the repository, unused by the normative path. `CITY_REGISTRY` rows each
carry their own country; `findCityBySegment` matched them exactly, with no country needed as input —
and its only callers were in the parser the SO spec marks non-normative. The new path had replaced it
with `useAtGeo = countryCode === 'AT'`, which needs the answer as its input. So the fix is a
restoration: `exactPlaceHits` matches the registry (and, when the country is unset or AT, the state and
municipality gazetteers), `classifyPlaceToken` derives the country when the hits agree on one, and the
AT-only *fuzzy* gate stays exactly where it was, because a near miss in one country's gazetteer is no
evidence of that country.

I made the registry lookup plural (`findCitiesBySegment`) before I needed it, because the interesting
case is a name in two countries, and a function that returns the first row cannot express it.

Two places where I departed from my own approved plan, both after the code made the alternative look
wrong:

- The plan said cross-country ambiguity should "write `city`, leave `country` null, record the
  candidate countries". There is no candidate-countries field, and inventing one would have duplicated
  something that exists: two values of one admin field is what `adminLevelMap` plus
  `adminLevelConflicts` is *for*. So every exact hit is written and the existing tray asks. Identical
  names collapse to one city with no country, which asks nothing it cannot answer.
- The plan listed a third provenance value, `narrowed`, for the org filter that is not built. I left
  it out. An enum member no code can produce is a promise in the type system.

One existing test had to change, and I want the reason on the record because the same shape went the
other way last time. `does not treat 4-digit token as postcode or house number without country` asserted
that `Wien/1090/Neustiftgasse-43/photo.jpg` yields no country and no postcode — which is exactly the
behaviour D-03 removes. In Phase 1.1 an existing test corrected *me* and I narrowed my rule; here the
spec the owner approved overrides the test, so I rewrote it into two: the derived case (`country=AT`,
`countryProvenance=derived`, `postcode=1090`) and the invariant it was really protecting, using a path
with no recognisable place (`Baustelle/1090/…` still yields neither).

### What it measured

`Graz/Annenstraße 10/DSC_0001.jpg` — the natural folder shape, and F-03's example — went from an
**empty** Search Object (`groupingKey |||||`) to `country=AT city=Graz street=Annenstraße
houseNumber=10`. At 500 generated paths: groups 391 → 442, `branch_a` 166 → 214, `layer_conflict`
277 → 229, trays 269 → 237, and camera vs neutral file naming stayed **identical**, so F-01's parity
survived the change. Classification also got faster (9.1 → 6.6 ms/file): the exact index answers
before a Fuse index is built.

The owner's path is the one worth quoting, because it is now what they had assumed the model already
was:

```
Mödling/Wilhelminenstraße 141/Wilhelminenstr 141, 1160 Wien.jpg
adminLevelMap:       city@[L2:Mödling L0:Wien] country@[L2:AT] state@[L0:Wien] postcode@[L0:1160]
adminLevelConflicts: city
groupingKey:         adminConflict|city|modling,wien
```

`Mödling` derives `AT` at level 2; with a country in hand `1160` is a postcode and `Wien` is a city, so
the level map holds both cities *with their levels* and the contradiction becomes the tray question it
should always have been.

### Two things this surfaced

Curated tray questions went 9 → **12**. Up, and correct: three paths that used to classify to nothing
now carry a real address whose folder and file name disagree, and asking is the right outcome. A
number moving the "wrong" way is only bad if the thing it counts got worse.

F-14 is now what stands between a curated run and a clean one. Run A leaves one job in `dedup_check`,
the harness waits out its full 180 s settle deadline because of it, and the suite exits non-zero on
the illegal `hashing → awaiting_disambiguation` transition. This change neither caused nor fixed that
— it was already reachable at curated size after the exact-match fix earlier today — but with
classification correct there is nothing else left, so Phase 1.7 moves ahead of 2.2. Twice now,
fixing classification has exposed a queue-ordering defect that was never in the classifier: it was
hidden by Search Objects too empty to register a conflict in the first place.

The ambiguity test I wrote *after* the code — one of the two I added for completeness rather than
red-first — caught a hole in the implementation, which is the argument for writing it at all. My hit
collector deduplicated by `kind:value` and only then recorded the country, so two registries spelling
one place identically (`Berlin` in the city registry, `Berlin` as an AT municipality in the fixture)
collapsed to one hit and the second country was never counted: the code derived `DE` from a name that
two countries claim. The country is a property of the *hit*, not of the value, so it is now counted
before the deduplication. The full suite found it, not the file I had been running.

I also narrowed my own findings checker again. `SO-FILENAME-OVERRIDES-FOLDER` fired on the owner's
path, where the pipeline records the conflict and opens a tray — i.e. working as specified — and its
message still said "a number in the file name", which is not what it had caught. It now skips fields
listed in `adminLevelConflicts` and says what it means: only a **silent** override is a finding.

## Phase 1.7 — the stranded job, and the two defects behind it (F-14, F-16, F-17)

The plan said "make the gate authoritative rather than a phase label a later step can erase, and only
then reconcile the FSM map". That turned out to be the right order for a reason I had not anticipated.

The hold is `disambiguationGroupId` + `resolutionStatus: 'pending'` — both halves, because a
layer-package re-resolve sets `pending` with no group id and that is work in progress, not a job waiting
for an answer. Pre-resolve now tests that, not the label, at entry and again after the dedup step (the
window the async registration actually lands in), and one `holdJob` exit re-asserts
`awaiting_disambiguation` whenever the hold is set, so a label another step overwrote is restored where
the job parks.

Then the interesting part. With the park in place, the curated run produced a **failed** job where it
used to produce a stranded one: `illegal transition awaiting_disambiguation → dedup_check`, thrown by the
Vitest reporter and turned into `upload_error`. The park had exposed the mirror image of F-14 — the dedup
step relabelling a job that was already parked. So the dedup step now skips the relabel for a held job
(the dedup work still runs). Only after that did I add `hashing → awaiting_disambiguation` to the map:
adding it first would have silenced the one signal that was telling the truth.

I also nearly shipped a false claim in the same change. F-14's write-up cited a sibling edge,
`hashing → conflict_check`, as evidence of the same family "on the unmodified tree". Adding it to the map
broke two specs — because that edge is the *example* both FSM specs use for an unmapped one. The line in
the full-suite log had been my own test fixture all along. The edge is out of the map again and the claim
is retracted in STUDY-005.

### The job that was actually stranded

After all that, run A still had one job in `dedup_check`: S09,
`AT/Wien/1010/Kärntner Straße 4/Top 3/IMG_6001.jpg`, with coordinates resolved and no tray of its own.
It was never F-14. `handleResolvedPreResolve` applies one group's geocode to every job in the group, and
it returned `'held'` the moment *any* job in the loop was held — to a caller that is one specific job's
pipeline run. S09 inherited the verdict of its sibling S13, whose camera GPS is 200 km from its folder
address and which does belong in a source-conflict tray. Two bugs in one `return`: the asking job parks
with no hold of its own, so nothing can ever resume it, and the loop exits early, so jobs after the held
one never get the group's placement.

Source conflicts are per job by construction — `isJobEligibleForSourceConflictGroup` requires both a text
pin and an EXIF pin, and S09 has no EXIF, so it had already been excluded from that tray's scope. The fix
is three lines: remember whether the *asking* job was held, and run the loop to the end. Filed as F-16,
red-first with three cases, two of which were red.

Run A now settles with 0 jobs in an active phase and no illegal-transition report — Phase 1.7's stated
acceptance criterion — and S09 uploads.

### One more thing the fix surfaced, left open

Run B's skip count went from 1 to 2. I checked instead of assuming: run B **alone** skips 1, run B after
run A skips 2, the hashes are byte-identical in both orderings, and the extra skip is S13 — the file run
A parks in a tray, whose hash is unique in the corpus. A parked job has already reserved its content hash
in the in-flight dedup registry, and the reservation is released only on a terminal phase. So while a
user thinks about one tray, another file with the same bytes can be skipped as a duplicate of a file that
was never uploaded. Filed as F-17 with the mechanism marked inferred, because what the harness proves is
the leak, not yet the production path. Anyone reading run B's numbers should read that second skip as
this artifact, not as a second duplicate in the corpus.

## Rethinking the Search Object: evidence, derivation, and a view (F-04, F-11)

The owner said the Search Object "doesn't fill like I want it to", and asked whether we should fill
empty fields from other fields or keep only what the path literally said. Looking at the measured
object, both options were wrong, because the object was being asked to be four things at once: the
geocoder query, the grouping key, the panel label, and the record of what the path said. Those want
opposite content — a derived city helps a query and poisons a key — and reading all four off one set of
flat fields is why no value's meaning was clear. `city = Linz` could be a folder the user typed or a
postcode expansion, and nothing said which.

So the model is now three layers, written down before any code: **evidence** (literal, per folder
level, several values per field, never invented), **derivation** (a value computed by a *named* rule,
carrying the rule and what it came from), and the flat fields as a **view** computed from those by
explicit precedence. A rule that cannot be named is not a derivation, it is a guess, and guesses are
not written.

They were also right about the vocabulary. "Admin fields" means the administrative hierarchy that
*contains* an address, so the spec now says **area** (country, state, postcode, city) versus
**address** (street, number, staircase, door). The tray kind string and its seeded translation key
keep their old spelling, because renaming those is a translation migration, not a model change.

### What the measurement showed once I looked properly

The flat `street` was a **concatenation of leftovers**. `Baustelle Nord/Mühlenstraße 12.jpg` produced
`street = "Baustelle Nord Mühlenstraße"`; `Rohdaten/Kamera A/IMG_9001.jpg` produced
`"Rohdaten Kamera IMG"`. Any word a classifier could not place became a street fragment at confidence
0.5, and the builder appended it to whatever was already there. That is the mechanical reason the field
looked arbitrary — it was not a street, it was the residue of the whole path.

And `Baustelle Süd/Woche 12` produced `houseNumber = 12`. A week number. It reached the grouping key,
so unrelated files could be grouped by a stray number.

### The rules that fixed it

Street evidence is **strong** only with a street suffix or keyword, with the `str`/`str.` abbreviation
(so `Wilhelminenstr` counts), or from a house number standing beside it in a segment that is not
noise — never for a camera label, since `IMG_1` also has a number beside a word. Weak evidence stays in
`sources` and may still be shown in a tray, but it never becomes the flat street and never forms an
address package. A package requires a street at all, because a lone house number describes a position
on a street nobody named. And a file name may only write address fields when it carries a street of its
own, which is [F-01](../study/005-upload-pipeline-trace-findings.md#f-01)'s rule applied to the address
side: without it `Wilhelminenstr 141/IMG_1.jpg` let the camera counter `1` overwrite the folder's 141.

Two small things carried real weight. Period folders (`Woche`, `KW`, `Tag`, `Monat`, `Jahr`) are noise
segments now, which is what stops `Woche 12` from being promoted to a street by the adjacency rule. And
street comparison folds `str.` ≡ `straße` and `ß` ≡ `ss` — the layer-map spec had *claimed*
`Straße ≡ strasse` for months while the code compared them unequal, so the owner's own path was asking
whether `Wilhelminenstraße 141` and `Wilhelminenstr 141` are the same address.

### Measured

Curated corpus: tray questions **12 → 4**, files completing **5 → 13**, groups 15 → **11**.
`AT/Wien/1090/Währinger Straße 12` is one group of four files again. `Graz/Annenstraße 10/DSC_0001.jpg`
completes. The owner's `Mühlenstraße` requirement holds: `street=Mühlenstraße hn=12`, complete, and
both `Baustelle Nord` files share one group. Their `Mödling/…/Wilhelminenstr 141, 1160 Wien.jpg` keeps
`street=Wilhelminenstraße hn=141` and asks exactly one question — Mödling or Wien.

At 500 generated paths: `layer_conflict` **229 → 128**, `branch_a` **214 → 230**, trays **237 → 191**.
Seventy-five groups moved from a `layer_package` tray to "no address here". That is not a loss: the
question those trays asked was which meaningless string was the street. A file with GPS now uploads on
its EXIF, and one without lands in Issues where a person can place it — `Baustelle Süd/Woche 12` does
exactly that, and `Rohdaten/Kamera A` uploads on its camera GPS.

One existing test had to move with the model: the orchestrator's admin-conflict fixture used
`AT/Wien/Innsbruck/photo.jpg` and relied on `photo.jpg` being read as a street to reach `needsGeocode`.
It now carries a real street segment. Its assertion is unchanged.
